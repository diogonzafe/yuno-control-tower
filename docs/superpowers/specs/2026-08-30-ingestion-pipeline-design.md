# Ingestion design (consumer + rollups)

Consumes the Redis Stream that the generator (`packages/generator`, owned by
another team member) feeds at ~60 TPS, writes each transaction to
`transactions`, and keeps `rollup_minute` and `rollup_declines_minute` up to
date. It judges nothing — it only tallies (`roadmap.md` §2, "14:03 —
transactions come in"). Detection, diagnosis, and the narrator are out of
scope for this spec.

## Context

- The Postgres schema and migrations already exist and are applied
  (`context/schema.md` §7, `packages/app/src/db/schema.ts`).
- `packages/contracts`, `packages/generator`, and `packages/app/src/ingest`
  have no content yet — this spec covers `contracts` and `app/src/ingest`.
  `generator` is another team member's responsibility; this design only
  defines the contract the two sides share.
- Work isolated on the `feature/ingest` branch, created from `main` after the
  package skeleton (`592c5e1`), so as not to collide with whoever is building
  the generator in parallel.

## Architecture

```
generator (another team member)
    │  XADD stream:transactions * payload <json>
    ▼
Redis Stream "stream:transactions"
    │  XREADGROUP GROUP ingest app-1 COUNT 100 BLOCK 500 ... >
    ▼
packages/app/src/ingest/consumer.ts   ── read loop, XACK, XAUTOCLAIM
    │  batch of parsed, valid events
    ▼
packages/app/src/ingest/rollup.ts     ── aggregateDeltas() [pure function]
    │  deltas per cell
    ▼
Postgres: transactions, rollup_minute, rollup_declines_minute
```

`consumer.ts` handles everything Redis-related (group, reading, ack,
pending-message recovery). `rollup.ts` doesn't know Redis exists — it
receives a list of already-validated transactions and returns deltas, plus
exposing the upserts. This separation is deliberate: `rollup.ts` is the same
piece the cross-sectional cut and the retroactive scan (future phases) will
reuse (`rules.md` §1, DRY), and it must not carry anything
transport-specific.

## Event contract

See `flight_logs/transaction_event_contract.md` for the discarded options and
why. Summary of what goes into `packages/contracts/src/transaction.ts`:

- `transactionEventSchema`: Zod, mirrors the `transactions` columns 1:1
  (`schema.md` §7). `transaction_id` is generated by whoever produces the
  event — it is ingestion's deduplication key.
- Cross-field `.refine()`: `status === 'DECLINED' ⟺ declineCode` present
  (mirrors the `CHECK decline_code_consistency`); `paymentMethod === 'PIX' ⇒
  country === 'BR'` (DD5).
- Transport: a single `payload` field in the `XADD`, containing
  `JSON.stringify(event)`. The consumer does `JSON.parse` followed by
  `transactionEventSchema.safeParse`.

## Processing pipeline

See `flight_logs/micro_batch_ingestion_with_dedup.md` for the discarded
options and why. Flow summary:

**Setup (`consumer.ts`, at startup):**
`XGROUP CREATE stream:transactions ingest 0 MKSTREAM`, ignoring `BUSYGROUP`.
Starts from id `0` (not `$`) so as not to lose events emitted before `app`
finishes starting up. Consumer group `ingest`, consumer name `app-1` — only
one `app` process exists (`rules.md` §6.2).

**Main loop, per iteration:**

1. `XREADGROUP GROUP ingest app-1 COUNT 100 BLOCK 500 STREAMS stream:transactions >`.
2. Parse each entry: `JSON.parse(payload)` → `transactionEventSchema.safeParse`.
   Invalid ones are filtered out here (handled in the error-handling
   section).
3. Batch insert: `INSERT INTO transactions ${sql(validRows)} ON CONFLICT (transaction_id) DO NOTHING RETURNING transaction_id`.
4. Filter `validRows` down to the ones that came back in the `RETURNING` —
   only those are "genuinely new." Pass the list to `aggregateDeltas()` in
   `rollup.ts`, which floors `created_at` to the minute and sums
   `attempts`/`approved`/the three value sums per 5-dimension cell, plus the
   count per cell + `decline_code`.
5. Two batch upserts — one per rollup table — each a single
   `INSERT ... ON CONFLICT (pk) DO UPDATE SET attempts =
   rollup_minute.attempts + excluded.attempts, ...` statement covering every
   cell touched in the batch.
6. Steps 3–5 inside a single Postgres transaction (`sql.begin(...)`). `XACK`
   for the whole batch only happens after the commit.

**Assumed simplification:** `rollup_minute.latency_p50_ms` stays `NULL` in
this v1. The column exists in the schema, but `schema.md` §2 already marks
`latency_ms` as cuttable, and a correct incremental p50 without storing every
sample is real work for something detection doesn't use (Wilson doesn't
depend on latency). If time allows, it can be estimated in batch later with
`percentile_cont` — it doesn't block anything else in the system.

## Error handling and recovery

- **Malformed event** (`safeParse` fails): log at `error` with the raw
  payload and the reason, `XACK` anyway. One rotten message must not stall
  the whole group waiting to reprocess forever.
- **DB failure mid-batch:** the Postgres transaction didn't commit, nothing
  was done, there's no `XACK` — the messages stay pending in the consumer
  group's PEL. In-process retry with a short backoff (up to 5 attempts) over
  the same batch already parsed in memory. If it keeps failing, log at
  `fatal` and the process exits — there's no point keeping `app` up if
  neither ingestion nor detection can talk to the database.
- **Recovery on restart:** before the main loop,
  `XAUTOCLAIM stream:transactions ingest app-1 0 0` reclaims anything pending
  from a previous run and processes it through the same pipeline. Since the
  pipeline is already idempotent (`RETURNING` filters out what was already
  inserted), reprocessing a message that was committed but never
  acknowledged is safe: its rollup delta comes out to zero and it just
  receives the `XACK` it was missing.

## Tests

Writing order (TDD, `rules.md` §4 and §1):

1. `aggregateDeltas` (`rollup.ts`) — pure function, no database: a fixed
   batch of validated transactions → exact deltas per cell in
   `rollup_minute` and per cell + code in `rollup_declines_minute`. This is
   the test `AGENTS.md` already requires ("exact aggregates from fixed
   batches of events") and the most important of the three.
2. `transactionEventSchema` — table of valid/invalid cases, including both
   `.refine()`s (`decline_code` consistency, PIX⇒BR).
3. End-to-end idempotency — process the same batch twice against a real
   Postgres (the one from `.env`) and compare the rollups before/after the
   second pass: they must be identical. The only test that needs a real
   database; everything else is pure.

## Out of scope for this spec

Consumption of the rollups by the detector (absolute trigger, cross-sectional
cut, Wilson), UI, and anything in `packages/generator`. The
`aggregateDeltas` pipeline is designed to be reused by those future phases,
but implementing them is not part of this work.
