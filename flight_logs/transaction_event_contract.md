# Transaction event contract on the Redis Stream

## Options considered

- **Loose fields** as field-value pairs of the `XADD` itself (one pair per column).
- **A single `payload` field** with `JSON.stringify` of the full object.
- **Binary format** (protobuf/avro), with a schema registered separately.

## What we chose

A Zod schema in `packages/contracts/src/transaction.ts`, mirroring 1:1 the columns
of `transactions` (`schema.md` §7), carried as a single `payload` field (JSON) on
the stream. The `transaction_id` (UUID) is generated by whoever produces the event
— it is the deduplication key against consumer-group redelivery. Two cross
validations go in as `.refine()` on the schema itself, rather than relying only on
the Postgres `CHECK`: `status`/`decline_code` consistency, and
`payment_method = PIX ⇒ country = BR` (DD5).

## Why

- Redis Streams only store strings in fields. Spreading individual fields forces
  you to rebuild the type field by field on read (number/boolean/null become
  string) — a risk of a silent coercion bug. A single payload + Zod does the
  coercion once, at the entry point.
- Protobuf/avro would give a more compact payload and a versioned schema, but they
  require an extra toolchain (code generation, schema registry) that does not pay
  off on a ~60 TPS stream in 24h.
- Mirroring `transactions` instead of inventing a bespoke event shape avoids a
  translation layer (event → DTO → database row) maintained by hand; the Zod
  schema *is* the table's input validation.
- **Accepted cost:** the generator is coupled to the database schema by
  construction — if a `transactions` column changes, the contract changes on both
  sides at once. Deliberate: the generator already reads from the same Postgres to
  build valid combinations, so the coupling was there in fact already.
